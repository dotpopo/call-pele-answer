# 文字规则：STE 风格

只用受控语言的**结构规则**（句子形状），不带词典。词汇只作方向：用最平常的词，同一个东西始终用同一个名字。

## 两种模式（frontmatter `ste:`）

| | flavored（默认） | strict |
|---|---|---|
| 用于 | 解释、比较、复盘、README | 操作步骤、工具描述、错误信息、Agent 间指令、安全相关 |
| 中文句长 | 步骤 35 字 / 描述 45 字 | 步骤 30 字 / 描述 40 字 |
| 英文句长 | 步骤 20 词 / 描述 25 词 | 同左 |
| 分号 | 允许 | 不允许（STE Rule 8.1） |
| 一义一词 | 自己保持一致 | CLI 检查同义词表（单击→点击 等） |

## CLI 检查什么

- 句长、段落 ≤ 6 句（**正文段落、列表、表格单元格、引用、交互块里的文字都查**）
- 一句里“的” ≥ 4 个
- 轻动词：进行X / 加以X / 予以X / 做出X → 直接用 X（不误报“制作出来”）
- 空话：赋能、抓手、闭环、至关重要、综上所述、值得注意的是……
- 开场白和客套结尾：“下面我来介绍”“希望对你有帮助”
- 列表以“等 / etc.”结尾 → 列全，或说明完整清单在哪
- 错别字：帐号→账号、阀值→阈值、布署→部署
- 无数量词：尽快、若干 → 写出期限、数量
- 英文：短语动词（spin up）、营销形容词（seamless、robust）、名词化（perform an analysis）、垫话（in order to）、步骤里的被动语态（提示）

## CLI 刻意不查什么

- **语气词**：可能、大约、约、may、might、could。它们表达作者的把握程度，是内容不是风格。把“可能失败”改成“失败”，是换了一个断言。
- “数字 + 以上/以下”：在多数解释里不会造成误解；需要精确边界时自己写“不少于/大于”。

## 豁免写法

- 行内代码、公式、`~~删除线~~`、状态为 `no` 的表格行：不查。
- 引号里的词（“赋能”「闭环」）是在**谈论**这个词，不查。
- 整段豁免：`<!-- ste-off -->` 到 `<!-- ste-on -->`。

## CLI 查不了、要自己守的

1. 结论先行：第一句给答案。
2. 一句一个事实；一步一个动作，条件放前面：“构建失败时，看日志。”
3. 同一个东西全文一个名字，第一次出现时解释。
4. 指代明确：不用指向不明的“它/这个/上述”。
5. 事实、推断、假设、示例分开写。
6. 简化不丢精度：否定、条件、单位、适用范围一个不删。宁可长一点，也不丢条件。
7. 警告在前：先说不要做什么，再说原因。
8. 不描述自己怎么工作的（“我先读了文件……”）。给结果和证据：路径:行号、命令、数字。
9. 内容空洞时，STE 救不了它：直接说没有可说的。
