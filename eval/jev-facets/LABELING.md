# 标注准则：一块该不该画、画哪种

依据：表达性原则（Mackinlay 1986）——图只表达文字里有的事实，且全部表达。删除测试——删掉图，读者丢不丢信息。

## 总规则
1. 默认 prose。图要自己证明：它让读者看出文字一眼看不出的结构。
2. gold 写首选；第二个及以后是“也可以接受”的形式，必须同样通过下面的条件。
3. 只看这一块的文字，不看原稿作者当时画了什么（作者画错是常见失败）。
4. 编号不等于顺序。建议、要点、优先级、待办清单，各项互不依赖 → prose。

## 各形式的进入条件（文字里必须能指认出来）
- table：≥3 项 × ≥2 个相同属性，或 2 项 × ≥3 个属性，读者要横向比较。2 项 × 1 个属性 → prose。
- bar：≥3 个可比项，同一单位的数字，比较大小就是这块的重点。数字只是附带说明 → 不画。
- line：同一指标 ≥3 个时间点。
- steps：≥3 个必须按顺序做的动作，后一步依赖前一步（操作说明、执行流程）。
- flowchart：有分支（条件不同 → 下一步不同），并且有汇合、回到前面的循环，或 ≥2 处分支。只有一句“失败就重来”的线性计划 → steps 或 prose。
- swimlane：≥2 个角色，且角色之间来回交接 ≥2 次。只是“各自负责什么” → prose 或 table。
- sequenceDiagram：≥2 方互发 ≥3 条消息/请求，顺序是重点。
- stateDiagram：同一对象 ≥2 个命名状态，且写了状态之间怎么切换（含切回）。
- tabs：2–3 个并列方案/选项，各自有同样形状的细节，读者一次看一个。
- mindmap / treeView：一个主题分成命名的部分，各部分还有子项；目录或文件树 → treeView。
- callout：一条独立的警告或必须注意的事，脱离正文也成立。
- 领域图（requirement、erDiagram、classDiagram、railroad、usecase、c4、gantt、timeline、radar、sankey…）：只有文字明确是该领域的内容（有需求编号、字段、类、语法规则、权限、外部系统、工期、日期、多维评分、流量）才算。

## 常见陷阱（来自已审过的失败稿）
- 计划/建议清单里有“如果…就…”：一处条件不构成流程图。
- 三个角色各干什么：没有交接 → 不是泳道图。
- 结果汇报里出现若干数字：不是柱状图，除非这些数字是同单位、可比的一组。
- 把表格内容改写成句子后的“- 名称：属性 值，属性 值”列表：仍是 table。
